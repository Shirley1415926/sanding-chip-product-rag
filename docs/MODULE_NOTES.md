# 模块设计说明

## 1. Markdown 导入与 Metadata 校验

解决什么：让可审核的商品/规则/FAQ 资料以统一格式进入知识库，并能在回答后追溯。
输入 → 输出：带 front matter 的 `.md` 文件 → `SourceDocument(text, metadata)`。
为什么：第一阶段避免 PDF/OCR 的不确定性；在入口强制 `source`、`source_url`、`product_id`、`document_type`、`updated_at`，比后置补齐更可审计。

## 2. 自研语义/递归切分

解决什么：避免把型号参数、MOQ 与限制语句拆散，造成检索命中却缺少条件。
输入 → 输出：一个 `SourceDocument` → 一组带标题路径与字符位置的 `Chunk`。
为什么：优先按 Markdown 标题、段落和中英文句末符切分；只有单元仍超长才降级切字符窗口。该实现不依赖 LangChain，业务规则可直接测试和调整。

## 3. Embedding

解决什么：将中文自然语言问题与资料片段映射至可比较的向量空间。
输入 → 输出：文本列表 → 同维 `list[list[float]]`。
为什么：生产默认使用本地 Sentence Transformers 中文模型以获得语义检索；通过协议隔离模型依赖，验收时可注入确定性测试向量而不请求外网。

## 4. Chroma 向量库

解决什么：持久化 chunk、Metadata 和 embedding，并完成 Top-K 近邻查找。
输入 → 输出：`Chunk + vector` 批量 upsert / `query vector + k` → `RetrievedChunk`。
为什么：Chroma 本地持久化适合 MVP；同一 `source` 先删后写，使再次导入不会积累旧版本 chunk。

## 5. 检索与安全门

解决什么：区分“有证据可回答”与“必须由人工确认”的请求。
输入 → 输出：问题 → 风险判定或按分数排序的 Top-K 证据。
为什么：库存、具体交期、订单级/批量/经销报价与未提供的食品资料不能从静态知识库推断；明确商品名时只把该商品 chunk 交给回答层，明确属性又无文字依据时转人工。

## 6. 上下文受限 LLM 回答与来源

解决什么：把多个片段组织成简洁回答，同时保留可核验出处与目录 URL。
输入 → 输出：问题 + Top-K context → `AnswerPayload(answer, sources, handoff_required)`，其中每项来源含 `source_url`。
为什么：LLM 只接收编号后的检索片段和禁止补全指令；来源由程序从真实检索结果生成，不交由模型臆造。

## 7. CLI、样例与商城目录验收

解决什么：让非 Web 环境也可重复跑通闭环并检查商城事实与人工转接边界。
输入 → 输出：商城目录资料/问题/18 题 fixture → JSON 结果与退出码。
为什么：先用小而可复现的命令行闭环验证资料结构、来源 URL 与安全策略，复杂测试体系留到下一阶段。

## 8. 商城目录资料替换

解决什么：让知识库业务内容与真实商城展示对齐，并消除技术阶段 SDX 电子产品样例对回答的污染。
输入 → 输出：已给出的商品目录事实与平台入口事实 → 10 份商品 Markdown 和 1 份平台合作 Markdown。
为什么：每份资料只记录公开的产地、包装、展示价、规格、起订量或明确使用属性，并把未提供的食品、报价、库存、交期、入驻与售后信息转人工；这样可追溯且不会把缺失资料补成承诺。
